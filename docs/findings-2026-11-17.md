# Findings from first bring-up on an old Intel Mac (2026-11-17)

Test machine: MacBook with Intel Core i5-5250U @ 1.6GHz, 4GB RAM, macOS 12.7.6.
This was a secondary/throwaway checkout (`~/nfc-scan-2`, separate from the
existing `~/nfc-scan`) used specifically to test setup-from-scratch on
constrained hardware. Not the main machine — findings below are meant to be
triaged there.

---

## 1. Fix: `requirements.txt` — unpinned `onnx` breaks `make setup` on older macOS

**Status: fixed in this checkout, worth upstreaming.**

`insightface` pulls in `onnx` as a transitive dependency, unpinned. Releases
after `1.18.0` only ship wheels for macOS 13+. On macOS 12 (or any platform
without a matching wheel), pip falls back to building `onnx` from source,
which fails — its C++ uses `std::to_chars` for `float`/`double` in a way this
machine's Xcode Command Line Tools' `libc++` rejects (`error: call to deleted
function 'to_chars'`).

This is the exact same shape of problem the file already works around for
`onnxruntime` (see the existing comment above it) — `onnx` just never got the
same treatment.

**Fix applied:**

```diff
+# insightface pulls in onnx unpinned; releases after 1.18.0 only ship macOS 13+
+# wheels, so on this older Intel Mac pip would try to build it from source and
+# fail (its C++ uses std::to_chars in a way this Xcode CLT's libc++ rejects).
+onnx==1.18.0; sys_platform == "darwin" and platform_machine == "x86_64"
+onnx; sys_platform != "darwin" or platform_machine != "x86_64"
```

Verified `onnx==1.16.1`, `1.17.0`, and `1.18.0` all ship a `macosx_*_universal2`
wheel for `cp311`; `1.18.0` is the newest one that still does, matching this
exact macOS 12.7.6 box (`macosx_12_0_universal2`). `1.18.0` is what's pinned.

**Suggested action:** cherry-pick this diff into a real PR — it's a
platform-compatibility fix with no behavior change on machines that already
work.

## 2. Not a bug, but a footgun: `TAP_URL` default port doesn't match `make dev`/`make dev-cam`

`backend/serial_reader.py` defaults `TAP_URL` to `http://localhost:8000/tap`,
but `make dev` / `make dev-cam` / the documented manual run all use port
**8001**. Running the reader without explicitly setting `TAP_URL` silently
posts taps nowhere useful (connection refused, taps queue in
`failed_taps.jsonl`).

`docs/operations.md`'s "Running by hand" section *does* show
`TAP_URL=http://localhost:8001/tap` — so this is documented, just easy to
miss if you only skim the Makefile. Low priority, but changing the default to
`8001` (or reading it from the same place the backend's port comes from)
would remove a footgun for anyone bringing up a second/dev instance by hand.

## 3. Dev-only workaround, do NOT upstream: `docker-compose.yml` container names

Running a second checkout of this repo on the same machine (to test
setup-from-scratch without touching the real `~/nfc-scan` install) hit a
container name collision: `docker-compose.yml` hardcodes `container_name:
nfc-scan-postgres` / `nfc-scan-backend`, with no project-name prefixing. Two
checkouts therefore can't coexist even if Compose's own project/volume
namespacing (which *is* name-prefixed) would otherwise allow it.

Worked around locally by renaming to `nfc-scan-2-postgres` /
`nfc-scan-2-backend` in this checkout only. **This diff should not be
upstreamed as-is** — it's specific to running two copies side by side on one
box, which isn't a normal deployment shape. If multi-checkout dev ever
becomes a real use case, the proper fix would be dropping `container_name`
entirely and letting Compose's project-prefixed naming handle it, or deriving
the name from `COMPOSE_PROJECT_NAME`.

(Host port 5433 stayed as-is, matching `.env.example`'s `DB_DSN` — only the
*names* changed, not the port.)

## 4. Investigate: liveness scores are suspiciously uniform regardless of input

Every face the liveness (MiniFASNet anti-spoof) model scored during this
session — including live, enrolled, correctly-matched people (`ymr`, `drei`,
taps that were `ACCEPTED`) — landed in a narrow **0.012–0.017** band. That's
suspicious: a working model should separate live faces from spoofed ones by a
much wider margin, not cluster everything near zero regardless of who or what
is in frame.

Currently harmless in practice: `LIVENESS_THRESHOLD` is unset in `.env`, so
per `docs/operations.md`, the matcher only *logs* the score and uses the
model's own live/spoof verdict advisory-only — it never turns a matched face
into a rejection. But if `LIVENESS_THRESHOLD` is ever set based on calibration
assuming a wider score spread, or if someone trusts the raw number at face
value, this will misbehave.

**Not yet root-caused.** Candidate causes, cheapest to check first:
- Never calibrated — `docs/operations.md` explicitly says to run
  `python -m backend.calibrate --metric liveness` before trusting the
  absolute score; this was never done on this box.
- Lighting/webcam quality on this specific machine (built-in FaceTime HD
  camera, indifferent lighting) — worth repeating the test on the main
  machine's camera before assuming it's a code bug.
- A preprocessing mismatch in `backend/liveness.py` (crop/scale fed to the two
  MiniFASNet variants) — worth a closer read if calibration on a known-good
  camera still produces a flat ~0.01-0.02 band.

**Suggested action:** run `make calibrate --metric liveness` on the main
machine with a handful of genuinely live and genuinely spoofed (photo/screen)
samples, and see if the *spread* between them is wide enough to threshold on.
If live faces still score near-zero there, open an issue against
`backend/liveness.py` specifically.

## 5. Investigate: face tracker loses continuity under load, flooding the review queue

**Symptom:** one person standing in front of the camera for about a minute
generated **98 separate `tailgating` review-queue rows**, not one.

**Root cause chain:**
- This test machine is resource-starved: 4GB RAM, and with Docker Desktop's
  VM (~1GB) plus the Python/insightface/onnxruntime process running, free
  RAM sat at 20-90MB with 150MB-1.1GB in swap, fluctuating.
- `PERCEPTION_FPS` (loop-rate cap, default `15`) could not be sustained. Frame
  delivery was bursty — gaps of 9 to 48 seconds observed between face-detect
  events, instead of a steady ~66ms cadence. `sysctl vm.swapusage` and `top`
  showed ~27% system CPU time during this, consistent with page-fault/paging
  overhead rather than real inference work.
- `backend/matcher.py`'s dedup relies on `backend/perception.py`'s
  `FaceTracker` matching the same person across *consecutive* frames via
  bounding-box IoU (`TRACK_IOU_THRESH=0.3`). When frames arrive in sparse
  bursts after multi-second stalls, a person's head has moved too far between
  frames for IoU matching to hold, so the tracker assigns a new `track_id` —
  and the matcher's `_settled_tracks` dedup (comment: "a later PendingFace for
  such a track is the same continuous dwell... not a new cardless person")
  never fires, because as far as the tracker can tell, it IS a new person.

**Mitigation applied (this session):** dropped `PERCEPTION_FPS` from `15` to
`5` in `.env`. This cut the flood rate roughly 12x (98 events/65s → ~21
events/166s) but did not eliminate it — clusters of near-duplicate entries
(sub-second apart) still occurred.

**Suggested action for the main machine** (which presumably has more
headroom, so this may simply not reproduce — worth confirming first):
- If it does reproduce: try loosening `TRACK_IOU_THRESH` (e.g. `0.3` → `0.15`
  or lower) so the tracker tolerates more inter-frame movement before
  dropping continuity — this targets the actual cause (lost tracking) rather
  than just slowing the whole loop down.
- Consider whether `matcher.py`'s tailgating dedup should have a time-based
  fallback (e.g. "another tailgating outcome for an unmatched face within N
  seconds, no known track continuity, same rough bbox position → still treat
  as the same incident") independent of `track_id` continuity, so a dropped
  track doesn't automatically mean a new review row.

**Update, same day:** an older, unpushed checkout (`~/nfc-scan`, since
archived) turned out to have a commit addressing this exact symptom
(`3a61812`, "dedupe repeat tailgating verdicts for one continuous presence").
Attempted to cherry-pick it in — it's fully redundant. This checkout's
current `matcher.py` (from the `PC-033` camera-reopen work, `a1008e8`)
already implements the same per-`track_id` settle logic, and in a more
complete form (`_settled_tracks` is settled by *either* a claimed tap or a
tailgating flag, where `3a61812`'s `_tailgated_tracks` only covered
tailgating-after-tailgating). Two other commits from that same checkout
(`8c52b982`, a `/tap` 500 fix for pgvector's `Vector` wrapper; `d189b58`, the
face-goes-stale-before-a-late-tap fix) were also fully redundant — same
fixes, already present under different commit hashes.

**This confirms the diagnosis above, it doesn't change it.** The matcher-level
dedup already exists, in a stronger form than the old fix even had, and it
*still* didn't stop today's flood — because the real failure is upstream, in
the tracker losing `track_id` continuity, not in the matcher's dedup logic.
No code fix was carried over from the archived checkout; the `TRACK_IOU_THRESH`
suggestion above remains the open action item.
